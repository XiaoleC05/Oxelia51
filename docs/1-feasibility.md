## 1. 项目背景

### 1.1 问题陈述

AI 编码工具（Claude Code、Cursor、GitHub Copilot）的普及带来了 Token 消耗的爆炸式增长。开发者面临三个痛点：

1. **不可见**：不知道每次对话、每个项目、每天消耗多少 Token
2. **不可控**：没有预算预警，月底收到账单才知道花了多少钱
3. **不跨平台**：Claude Code 用一套、Cursor 用另一套，数据分散无法汇总

### 1.2 现有方案评估

| 方案 | 接入方式 | 自部署 | 国内 LLM | 代码语言 |
|------|:--:|:--:|:--:|------|
| Langfuse (MIT) | SDK 埋点 | ✅ 复杂 | ❌ | TypeScript |
| Helicone (Apache 2.0) | 代理/SDK | ✅ 中等 | ❌ | TypeScript + Rust |
| Weights & Biases | SDK | ❌ | ❌ | Python |
| LLM Report (闭源) | 代理 | ❌ | ❌ | — |
| **本项目** | **代理** | **✅ 一键** | **✅** | **Go + C++** |

### 1.3 项目目标

构建一个 Token 用量监控平台，做到：
- 改一行环境变量即可接入，不装任何 SDK
- 5 分钟自部署，数据不离开用户服务器
- DeepSeek/Moonshot/智谱等国内模型开箱即用
- Go + C++ 技术栈，有简历区分度

### 3.4 数据采集方案

**主方案**：API 代理模式。用户将 `ANTHROPIC_BASE_URL` 或 `OPENAI_BASE_URL` 指向 `oxelia51.com/api/proxy/<provider>`，Go 代理网关在转发请求时：
1. 从请求头提取 `X-Project-ID`（项目标识）和 `X-Session-ID`（会话标识）
2. 解析请求体中的 `model` 字段
3. 转发到上游 LLM
4. 接收响应：普通 JSON 直接解析 `usage` 字段；SSE 流式从最后一个 chunk 提取
5. `go recorder.Record()` 异步写入 ClickHouse
6. 原样返回响应给客户端

**辅助方案**：定时调用各 LLM 供应商的 Usage API 做交叉校验，防止代理层统计遗漏。

**用户改动量**：一行环境变量。

### 3.5 性能估算

```
Go 代理网关（单核 2GHz）：
  - HTTP 转发延迟：< 5ms（本地回环）
  - 并发连接数：goroutine 模型，单机可支持 10,000+ 并发
  - 内存占用：~10MB（二进制） + ~50MB（运行时）

ClickHouse（4C4G）：
  - 写入吞吐：10,000+ 行/秒（单节点）
  - 查询延迟：30 天范围聚合 < 100ms
  - 压缩比：原始数据 10-20x 压缩

容量预估：
  - 日请求 1,000 → 年数据 365k 行 → ClickHouse 压缩后 ~50MB
  - 日请求 10,000 → 年数据 3.65M 行 → ClickHouse 压缩后 ~500MB
  - 日请求 100,000 → 年数据 36.5M 行 → ClickHouse 压缩后 ~5GB
```
